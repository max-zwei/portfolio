## The root cause behind §14

Four of the six §14 corrections — post-it colours and geometry, NavBar column
alignment, white marks, and by extension the "is the component in
`src/components`?" question — have one cause:

**I checked for drift against a cache instead of re-reading the source.**

`design/components.json` carries `readOn: 2026-08-31`. The page was built on
9 Sep. Step 4 of the skill says to diff the library against that manifest — so I
diffed a ten-day-old set of _notes_ against a library that had been redrawn, and
the diff came back clean because the notes had not changed. The manifest records
what a set looked like; it cannot tell you the set has moved. Specifically:

| What I built from                                      | What Figma actually held on 9 Sep                                |
| ------------------------------------------------------ | ---------------------------------------------------------------- |
| Manifest note: one 218×246 box, 200×200 paper, 64 disc | Four per-variant boxes, 181 paper, 40 disc (`114:577`–`114:580`) |
| My own August port of `NavBar`                         | A redrawn two-column layout (`114:189`, `114:190`)               |
| One exported copy of each social mark                  | A dark instance painting every mark neutral-white                |
| `Buttons` with four Type values                        | A fifth axis, `Icon=ON` (`377:2215`)                             |

The other two §14 items are separate misreads, and both are read-order gaps:

- **Page ground.** The frame `103:1123` has its own fill — `#fdfcf8`, bound to
  `color/neutral/white`. I never read it. I inherited `global.css`'s
  `--color-neutral-100` body ground and assumed the page agreed. One property
  read would have caught it. Verified today, after the fact.
- **Full-bleed footer.** A 1280-wide frame cannot express "this element ignores
  the grid". I read the frame edge as the content edge and put the footer inside
  `.container`. Nothing in the file distinguishes the two; only prose can.

## What was missing for a clear handover

The Handoff frame did its job for _what the page is_ — §1–§12 are why prediction
1 held twice running. It is the **update mechanism** that is missing, and this is
now the biggest cost per round.

`375:1657` is a single text node, 5,727 characters, that grows a new section per
round: §13 `UPDATES`, §14 `FEEDBACK`, §15 `UPDATES 2`, §16 `FEEDBACK 2`. Four
consequences, all observed:

1. **No node ids on updated components.** "Updated the text style for the
   component `<CvSection>`" does not say which node, which text style, or what
   changed. Every such line becomes a full re-read of the set to find the delta.
   "Updated `CV section` (`114:640`) — role and company text styles" would be one
   targeted read.
2. **Design update and code correction are indistinguishable.** §13 mixes "I
   adjusted the layout of the Header" (a Figma change to read) with "add post its
   depending on the length of the combined section" (a code rule that exists
   nowhere on canvas). They need different work and the same sentence shape
   carries both.
3. **Superseded values stay live.** §13 says the sections went to 8 columns; §15
   says 7 "again". Read top-down — which is how a fresh agent reads it — §13 is
   implemented first and then reverted. The width has now been 10, 8 and 7 across
   three rounds with nothing marking which is current.
4. **Behaviour thresholds live in prose and churn.** "300-400px of vertical space
   between each post-it", "the middle 60% of the viewport", now "33% center
   height", "increase their size to 18px on hover". These are the values that
   change every round, and they are exactly the values with no variable, no node
   and no drawn state — so each one is a re-read of a paragraph.

**What would fix it,** in rough order of payoff:

- A `CHANGED SINCE LAST SYNC` section, replaced (not appended) each round, one
  line per item: `node id — what changed — [design | code-only]`.
- Strike or edit superseded lines in place. A reverted decision should not read
  as a pending one.
- Name the thresholds. If a number has changed once, it wants a name and a home:
  `focus band = 33%`, `note gap = 300–400px`, `mark hover = 18px`.

## Skills — what changed, and what still should

Applied to [`figma-to-astro.md`](../skills/figma-to-astro.md) in this commit:

- **Step 1 now reads the frame's own fill** before anything else. The
  neutral-100 ground was a one-property miss.
- **Step 4's drift check is a re-read, not a diff.** For every set the page
  actually instantiates, pull the current geometry and variant list from Figma
  and compare against the manifest — the manifest is the record, never the
  source. `readOn` is a staleness marker, not a guarantee.
- **A `## 4b. Re-sync jobs` section**, because rounds 2 and 3 are a different
  procedure from round 1 and the skill only described round 1.
- **Assets export per instance, not per component.** An SVG's fill is baked at
  export; the dark NavBar needed its own eight files (`public/icons/dark/`).
- **Traps**: the dev server needs Node ≥ 22 and `--base /`; the dev toolbar has
  to be hidden before any screenshot comparison.
- **Mechanics**: targeted read-only `use_figma` snippets are the cheap way to
  verify one property. See token usage below.

Still open, and both need Max:

- `docs/design-system.md` should state the site's default page ground now that it
  is neutral-white rather than neutral-100 — R5 says that document is Max's.
- `CLAUDE.md` §4's map does not mention `src/pages/resume/cv.astro` or that
  `/resume` and its PDF are now two different routes (R1 — proposal only).

## Token usage

I cannot produce this round's figures; they live in Max's usage export. The last
job's, for comparison: 40.7M cache reads, 68k output, $81.44, ~15 hours.

What is observable from inside the session:

**The single biggest saving found this round** was replacing `get_design_context`
with targeted read-only `use_figma` snippets for verification. Confirming the
page ground cost one call returning 60 bytes:

```js
{ name: 'Web', fill: '#fdfcf8', bound: true }
```

The equivalent `get_design_context` on that frame is a full React reference plus
asset URLs. Same for the mark colours, the Buttons variant matrix and the slot
fills — each a sub-200-byte answer to a specific question. **`get_design_context`
is for building a frame the first time. Every check after that is a plugin-API
read.**

Spent more than needed on:

- the Handoff text node — 5,727 characters re-read whole to find the new section;
- five Playwright probe runs printing overlapping JSON, where two would have done;
- one rejected edit hunk that forced a re-read of `design/components.json`;
- a full-page 1280×4698 screenshot when the header and footer crops were what the
  comparison actually used.

Spent well:

- one frame per `get_design_context`, never a page;
- structural file summaries and line ranges rather than whole components;
- measuring the dim transition during the build rather than after the report.

## Missing information about the site

Things I did not have, in the order they cost time:

1. **Which routes are print sources.** `npm run pdf` prints `/resume/cv`, not
   `/resume`, since the split — and `docs/resume.md` still said `/resume` in
   three places. Fixed here.
2. **The site's default page ground.** It was neutral-100 in `global.css`,
   neutral-white in the design, and nothing said which was the decision.
3. **Dev-server invariants.** Node 14 on the PATH and a missing `--base /` cost
   several turns before the server would serve assets at all.
4. **Which pages are designed and which are not.** The ground change in
   `global.css` reaches `/styleguide`, `/home` and every prose page. Nothing
   records whether those pages have a design that agrees.
